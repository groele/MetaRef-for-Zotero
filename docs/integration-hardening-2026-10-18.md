# 三组扩展能力整合复核与完善

本轮版本：10.7.0-beta.3。此前的设置分区与核心工作流说明见 `core-workflow-audit-2026-10-18.md`。本报告补充合并后的用户判断继承、导入并发与刷新效率。

## 兼容性结论

MetaFlow 已将三组能力纳入自身执行队列与设置界面：ZotMeta + DOI Manager 的核验补全、arXiv Workflow 的明确出版关系管理、Zoplicate 的去重决策及设置。插件不依赖这几个原插件运行。

不能将这一结论表述为“完美整合”或“原插件任意版本同时启用均无冲突”。本轮针对整合实现进行隔离宿主回归，没有安装全部原插件并测试其自动处理同时启用的组合。其他插件仍有自己的执行队列；MetaFlow 无法替它们串行调度写入。

## 本轮修正

| 问题 | 修正与执行边界 |
| --- | --- |
| A、B、C 都被识别为重复，用户已认定 B 与 C 非重复，但 A 合并 B 后可能继续合并 C | 经 MetaFlow 发起的原生合并成功后，将 B 的排除记录指向存续主条目 A；批量合并每一步重新检查排除关系，跳过 A、C。排除不作为批次错误处理 |
| 合并失败可能影响后续判断继承 | 仅在原生合并成功后迁移记录；失败保留原条目键与排除记录，并沿用已有缓存恢复 |
| 排除关系改变后统计标签没有立即收到重绘通知 | 写入时统一失效缓存并通知集合树重绘；同一轮连续写入合并成一次通知，未变化的判断不失效缓存、不重绘；统计计算仍按需执行 |
| 导出文件包含回收站条目的排除记录 | 仅导出仍有效的常规条目；本地原记录保留，条目从回收站恢复后原判断仍生效 |
| 导入逐个查询条目期间，另一窗口新增的判断被旧快照覆盖 | 查询结束后读取最新记录，再合并本次新记录并校验容量；并发加入的相同判断计为跳过，避免重复 |
| 每次合并都可能扫描所有排除记录 | 构建并缓存条目参与索引；被合并条目没有排除记录时采用集合查询直接返回。只在实际需要迁移时遍历记录；迁移去重后记录数量不增长 |

记录键迁移面向合并后存续的条目，不提供跨 Zotero 原生合并与偏好文件的全局原子事务，也没有新增合并撤销功能。原生条目合并和本地偏好记录仍属于不同存储边界。

## 功能入口与运行成本

继续保留两个默认菜单入口。检查负责本地格式与校验，联网核验、期刊指标、交互去重按设置选用；更新执行核验采纳并可继续本地整理。完整核验和作者核验共用查询，重复点击相同任务复用进行中的执行。

PDF 候选扫描、标题检索、正式版查询、交互去重仍默认不加入每次更新；全库批量合并、统计重算、排除记录导入导出继续由设置页明确触发。本轮没有增加自动全库扫描或隐藏网络请求。此次增加的排除继承在发生合并时执行，重绘不触发重算。

## 本轮验证

验证结果与生产安装包哈希见交付目录的 `verification.json`，完整输出保存在 `verification/`。本轮增加五个原生用例：排除关系阻止连锁合并、合并失败不迁移、回收站恢复、刷新合并、导入期间竞争写入。

最终通过 74 个文件中的 485 项单元测试；Windows Zotero 10.0.6 / Gecko 140 和 Zotero 11.0-dev.5+dac1ad489 / Gecko 153 各通过 136 项完整原生测试，均包含生产 XPI 安装验证。构建、TypeScript、ESLint、AutoCorrect 与差异空白检查通过。各宿主分别构建生产包，交付包为最后一次 Zotero 11 安装验证所用文件；验证清单同时保留 Zotero 10 构建包的哈希。

首轮完整回归暴露了连锁合并测试对创建时间和候选顺序的隐式假设。测试现明确设置三个不同的创建日期，并传入 A/B、A/C 的候选顺序，专门验证先合并 B 后继承排除判断的路径；保留原有合并次数、跳过次数、删除状态与导出记录断言。

外部服务测试使用受控响应，不能证明实时服务可用性。Zotero 11 范围限定为所测开发版；全部原插件共存矩阵、macOS/Linux 和大型文库长时压力测试仍未完成。
