# MetaFlow 增量架构改造与设置整合

本轮在 11.0.0 发布源码基础上开发 `11.0.1-beta.1`，先完成去重子系统及右键设置的改造。公开更新源仍指向正式版；历史 Release 和标签保留。

## 已实施的架构边界

| 层次 | 模块 | 职责 |
| --- | --- | --- |
| 纯匹配领域 | `review/duplicate-matching.ts` | 普通数据记录、候选索引、标识符归一化结果复用、类型化匹配事件；不访问 Zotero、数据库或界面 |
| 分组与决策 | `review/duplicate-policy.ts` | 并查集分组、主条目选择、跨类型合并约束 |
| 宿主适配与写入 | `review/duplicates.ts` | Zotero 条目读取、调度让步、AbortSignal、快照校验、原生事务与失败恢复 |
| 任务编排 | `review/duplicate-batch.ts` | 有界并发、暂停、停止、完成状态；进度观察者失效不提前结束数据任务 |
| 设置与界面 | `preference.ts`、`workflow-settings.ts` | 收集菜单显示选择和执行步骤，绑定既有偏好，不复制执行算法 |

实现使用 Gecko 140 已支持的 ESM、TypeScript 判别联合、生成器和 AbortSignal。匹配引擎输出候选及带阶段信息的检查点，宿主在检查点让出界面线程并响应取消。未来调整调度方式时可以替换宿主消费者，保持候选规则独立。

分组使用按集合大小合并及路径压缩，不再建立完整邻接表或使用参数展开遍历大组。分组辅助存储与不同条目数相关；组内条目按候选输入的首次出现顺序保留，主条目仍由用户设置的策略选择。移除了无调用方的 `retainedMaster` 转发函数和原 `policy.ts` 中的去重实现，所有内部调用已迁到独立匹配模块，不保留第二套算法。

宿主版本差异继续集中在选择接口适配处。插件身份和已有设置键继续沿用，避免架构改造丢失现有配置。

## 修复的数据与执行问题

- 进度回调抛错时，记录一次异常并移除该观察者；数据工作仍等待全部并发合并完成。
- 候选索引和匹配每 250 次处理发出检查点，即使没有匹配结果也能响应取消。
- 去重关联在进入事务后再次检查两个条目的快照，保存第二条关系前再次检查相应条目。
- 关联事务失败只重载实际修改过的关系及主数据；没有开始修改的条目不重载，无关的未保存字段得以保留。
- 已取消的决定不再写入“非重复”记录；关联操作不再读取无关的附件和笔记列表。
- 设置操作拒绝重复的运行中命令事件；修正合法并发输入后清除之前的错误提示。

## 设置合并

原来的“两个核心功能与耗时选项”和“右键菜单设置”合为“右键菜单与核心功能”。每条命令的显示开关与执行步骤放在同一张卡片内，继续使用原设置键。隐藏菜单不会关闭自动导入或改变工作流步骤。

选项明确显示为“Zotero MetaFlow：仅显示‘检查并修复元数据’和‘更新元数据’”。开启时隐藏额外条目菜单及当前不适用的位置选项；关闭后恢复已有的位置选择。字段右键菜单单独保留在同一设置区。

## 批量去重与无弹窗审阅

去重命令发现多对候选后，直接显示主界面内的重复组选择面板，可全选或逐组勾选，并按既有主条目策略批量合并。保留逐对审阅入口。未经勾选的组不修改，版本关系不进入批量合并；每次实际合并仍检查条目快照、当前匹配依据及非重复排除记录。批处理提供暂停、继续和停止，已提交操作保留，未开始操作停止。

元数据与版本处理现已改用 `review/automatic-policy.ts` 的自动判据，直接填充或保留原值，不再显示元数据审阅面板。重复文献选择仍使用 `review/panel.ts` 的主界面内嵌面板，随任务取消、主窗口关闭和插件卸载清理。

独立运行文件及分层缓存策略详见 [自动元数据填充与本地运行数据](automatic-metadata-and-runtime-cache.md)。该文也说明数据字段、保留期限、容量、备份恢复和验证边界。

## 验证与边界

控制数据基准比较正式版与本轮实现的匹配结果和顺序。500 条密集重复记录产生 124,750 对候选；精确测量及高扇出分组故障复现见本轮交付目录的 `performance.json`。这类 Node 基准不代表真实 Zotero 文库的固定加速倍数。

并查集减少了分组辅助内存，候选列表仍需保留待审查的配对结果；极端密集重复桶的配对数仍可能呈平方增长。本轮没有声称完成超大文库长期压力测试，也没有完成所有第三方插件共存、在线服务账户权限或所有未来宿主版本的验证。

测试代码额外修正了错误的设置读取及若干宿主重载类型声明，使独立的测试 TypeScript 检查也能通过。最终单元、原生场景、安装包哈希和未覆盖项以本轮交付目录的 `verification.json` 为准。
